# 内容类型模板

先在稿件头部写明类型，再按对应小节写。通用文案规则见 `social-copywriting`，门槛和查重见 `content-quality-gate`。各类型共同点：先交文字稿给用户确认，确认后再做图。

## A. 常青技巧

- 四类轮换，每次推荐标明属于哪一类：技巧和坑点 / 插件和工具对比 / 翻车和踩坑事件 / 能直接复制的配置模板。
- 写成通用技巧，不把某一个模型当唯一主角；只在交代来源时点名原帖讨论的模型。
- 不写当天突发新闻、额度重置、官宣（归 D）；不写单仓长篇架构拆解（归 `oss-deep-report`）。
- 选题来源：X / GitHub 近两周被多次提到、可信开发者实际用过的；开源调研推来但不够做深度报告的轻量项目；用户点名。与已发内容不重复，和复盘里表现好的类型对齐（对比、怎么选、带数字）。
- 稿中每条命令、配置、对比都要有 `verify/` 日志。
- 交付：选题信息 + 小红书文案 + X 一键链接。没有够格的选题就不出稿，不降成资讯口吻凑数。

## B. 工具 / Skill 测评推荐

- 优先小众、开发者才会用到的工具；大众办公向、只改风格或配色的工具不当卖点，等有明显前后效果再写。
- 必须有硬对比：同一任务装与不装、或两种做法的实际输出，多个样例、多次运行；在稿中交代基线和埋的 bug 是自己做的。
- 标题按偏好层的编号格式；标题只写对比能证明的效果，不夸大（例：别写「让页面不像 AI 做的」）。
- 结构：谁出的、装上后有什么用（开头一两句，封面也要让人一眼看出是干嘛的）→ 它解决什么问题 → 怎么装 → 对比实测（表格或前后图）→ 适合 / 不适合的场景 → 来源仓库。
- 不重复推荐已发过的工具（查已发清单）。

## C. 概念扫盲

- 面向只会提问式使用 AI 的普通人；从最基础的概念讲起，每篇只讲一个小概念。
- 平实说明文，不用比喻、故事、举例场景；解释放在图卡上。
- 避免长定语、书面词和翻译腔（如「作出判断」「基于概率」「输入」），用自然口语；删绕的交代句。
- 不预告还没发的篇目编号或内容。
- 正文末尾列「参考原文」并附链接。
- 用偏好层指定的固定模板出图。

## D. 新闻资讯 / 速报

- 只用官号、官网、官方 changelog 作一手来源；首发在 24 小时内。
- 结构：发生了什么（带原文链接和时间）→ 具体变化（额度、档位、版本）→ 对开发者的影响 → 原文。
- 图：官方公告截图 → 外部反应截图 → 受影响界面截图，截图铺满。

## E. 产品功能介绍

- 重心放在它是什么、怎么实现、原理是什么。
- prompt 写法这类技巧压缩成附录前的一页简介。
- 官方原文放最后几张作附录。

## F. 文章 / 博客解读

- 图卡包含「内容概览」（文章讲了什么）和「作者结论」两类卡。
- 正文开头先给文章概要，结尾落到作者的结论。

## G. 周报

- 每条一件事、一个一手来源、一句对开发者的影响；条目按影响大小排序。
- 只收这周还没单独发过的事：每条先对照已发清单（路径见偏好层），已经单独发过的整条删掉，条数不够就少收，不凑数；交付时列出删掉了哪几条、撞的是哪篇。
- 标题点出本周最大的一件事（≤20 字），正文 + 话题 ≤1000 字。

## 自查

```bash
head -3 <稿>.md | rg "类型[:：]"                          # 写明了类型
rg -n "参考原文" <扫盲稿>.md                               # C 类必须有
rg -n "第[一二三四五六七八九十0-9]+篇|下一篇|下篇" <扫盲稿>.md   # C 类应为 0 行
```
