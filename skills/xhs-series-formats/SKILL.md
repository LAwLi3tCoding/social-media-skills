# 内容类型模板

先在稿件头部写明类型和形式（见下方「形式选择」），再按对应小节写。各类型都不用问句式小标题。通用文案规则见 `social-copywriting`，门槛和查重见 `content-quality-gate`。各类型共同点：先交文字稿给用户确认，确认后再做图。

## 形式选择：写长文还是卡片图文

每个选题出稿前先定形式，写进稿件头部（如「类型：F 文章解读；形式：写长文」），交付时附一句理由。

- **写长文（小红书「写长文」）**：演讲解读、长文章 / 博客解读、需要分好几节展开的深度解读，读者要顺着论证读下去。写法见 `social-copywriting` §4.2，发布见 `xhs-publish`「写长文」。
- **卡片图文**：常青 Tips、新闻速报、榜单、Skill / 工具推荐、概念扫盲，读者翻几张图就能拿走要点。
- 拿不准时看内容量：几张图卡就能讲清的做卡片图文；需要多节连贯论证、图卡装不下的写长文。
- 长文封面用和内容相关的照片或图片（演讲者或活动照片、产品截图、项目界面等），不用纯文字卡片当封面；要求见 `xhs-card-design` §1。

## A. 常青技巧

- 四类轮换，每次推荐标明属于哪一类：技巧和坑点 / 插件和工具对比 / 翻车和踩坑事件 / 能直接复制的配置模板。
- 写成通用技巧，不把某一个模型当唯一主角；只在交代来源时点名原帖讨论的模型。
- 不写当天突发新闻、额度重置、官宣（归 D）；不写单仓长篇架构拆解（归开源项目深度拆解，不在本仓库）。
- 选题来源：X / GitHub 近两周被多次提到、可信开发者实际用过的；开源调研推来但不够做深度报告的轻量项目；用户点名。与已发内容不重复，和复盘里表现好的类型对齐（对比、怎么选、带数字）。
- 稿中每条命令、配置、对比都要有 `verify/` 日志。
- 转述某位作者的 Tips 时，标题带作者名（见 `social-copywriting` §3），X 版按 `x-posting` 做引用转发。
- 交付：选题信息 + 小红书文案 + X 链接。没有够格的选题就不出稿，不降成资讯口吻凑数。

## B. 工具 / Skill 测评推荐

- 优先小众、开发者才会用到的工具；大众办公向、只改风格或配色的工具不当卖点，等有明显前后效果再写。
- 必须有硬对比：同一任务装与不装、或两种做法的实际输出，多个样例、多次运行；在稿中交代基线和埋的 bug 是自己做的。
- 标题按偏好层的编号格式；标题只写对比能证明的效果，不夸大（例：别写「让页面不像 AI 做的」）。
- 结构：谁出的、装上后有什么用（开头一两句，封面也要让人一眼看出是干嘛的）→ 它解决什么问题 → 怎么装 → 对比实测（表格或前后图）→ 适合 / 不适合的场景 → 来源仓库。
- 不重复推荐已发过的工具（查已发清单）。

## C. 概念扫盲

- 面向只会提问式使用 AI 的普通人；从最基础的概念讲起，每篇只讲一个小概念。
- 平实说明文，不用比喻、故事、举例场景；解释放在图卡上。
- 用平实易懂的词：避免长定语、生僻术语和翻译腔（如「作出判断」「基于概率」「输入」），删绕的交代句；本类以平实为准，不追求书面化。
- 不预告还没发的篇目编号或内容。
- 正文末尾列「参考原文」并附链接。
- 用偏好层指定的固定模板出图。

## D. 新闻资讯 / 速报 / 榜单

- 只用官号、官网、官方 changelog、榜单官网作一手来源；首发在 24 小时内。
- 结构：一句话结论（发布了什么、谁上榜第一）→ 具体变化（功能、额度、档位、价格、版本、分数）→ 对开发者的影响 → 原文链接。
- 先出问题、后有补偿：同一官号先宣布问题或规则变更（如计费出错），后又宣布补偿、重置、上线等后续动作时，按时效选主线：补偿是刚发的实时消息、问题也才出不久，可以拿补偿当标题，但开篇要交代起因；问题已经过去几小时、补偿是后来才跟上的，标题、封面和开篇主线写问题（出了什么问题、对用量或产品有什么影响），补偿放正文后段或末页。写速报草稿前先核对同一官号当天和相邻的说明，不把后续动作写成和起因无关的独立事件。重大事件速报类监控（如有）的分类和草稿同样按这条。
- 官方发布新功能：写功能本身，即能做什么、怎么用、价格或额度；不围着官方帖子写（发帖时间、公告标题、点赞转发数）。封面用功能界面、效果截图或要点卡，不用帖子卡片。
- 榜单 / 评测：标题和封面对齐评测对象，评的是工具（如 Claude Code、Devin）就以工具为主，模型只作搭配说明；标题写明是哪个榜的最新排行（格式：「<榜单名>最新排行：<工具>居首」）。指标用正式叫法（「软件工程评测」「终端任务评测」）。先给爆点：谁居首、差距多大、有什么意外。
- 图：功能或结果截图、要点卡在前，铺满；官方公告截图作来源页放后面。
- 卡片讲事，不写成核查记录：每张卡说这件事的一部分（是什么、怎么发生的、意味着什么），不用「发布证明」「社区声明确认」这类取证式标签当标题；核查过程留在内部，不上卡（详见 `xhs-card-design` §2）。
- 简报 + 概念科普型资讯（如用户要求「简单提一下这件事，重点讲概念、场景和差异」）：插件数量（如 10000+）、套餐档位（Free / Pro / Max 等）、同步上线范围这类发布规格不当正文和卡片主线，需要时一带而过或放末页，篇幅留给概念解释、适用场景与差异对比。

## E. 产品功能介绍

- 重心放在它是什么、怎么实现、原理是什么。
- prompt 写法这类技巧压缩成附录前的一页简介。
- 官方原文放最后几张作附录。
- 产品上手介绍（尤其用户给了自己的使用体感）：初稿就写齐上手必备信息，不等用户一条条补：关键模式（能做什么、谁能用、怎么开）、订阅档位与价格、额度（含是否分池、刷新周期）、支付方式、账号 / 地区 / 网络门槛，以及档位附带的其他福利。先理清介绍逻辑（是什么 → 怎么开通 → 怎么用 → 和同类比），再落到卡片。用户体感和第三方榜单分开写；榜单上的代价数字（更贵、更慢、轮次更多）只作补充，不盖过用户体感，也不当对比卡标题。D 节「套餐档位不当主线」只用于简报 + 概念科普，不适用于上手介绍。

## F. 文章 / 博客解读

- 篇幅长、分节多的默认写长文（见「形式选择」），按观点和方法组织，不写成新闻报道。
- 图卡包含「内容概览」（文章讲了什么）和「作者结论」两类卡。
- 正文开头先给文章概要，结尾落到作者的结论。

## G. 周报

- 每条一件事、一个一手来源、一句对开发者的影响；条目按影响大小排序。
- 只收这周还没单独发过的事：每条先对照已发清单（路径见偏好层），已经单独发过的整条删掉，条数不够就少收，不凑数；交付时列出删掉了哪几条、撞的是哪篇。
- 标题点出本周最大的一件事（≤20 字），正文 + 话题须 ≤960 字（平台硬限 1000）。

## 自查

```bash
head -3 <稿>.md | rg "类型[:：]"                          # 写明了类型
head -3 <稿>.md | rg "形式[:：]"                          # 写明了形式
rg -n "参考原文" <扫盲稿>.md                               # C 类必须有
rg -n "第[一二三四五六七八九十0-9]+篇|下一篇|下篇" <扫盲稿>.md   # C 类应为 0 行
```
