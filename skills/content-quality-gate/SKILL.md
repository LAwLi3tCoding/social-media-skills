# 选题与质量门槛

宁少发，不凑数。不达标就留在素材库，不设日更配额。

## 1. 选题过滤

- 时效：新闻类只取首发在最近 24 小时内的事件；官号重新推广旧功能不算新闻。
- 旧功能确实值得讲：写成「认识 X」式介绍，正文写明不是新功能并注明首发与上线时间。
- 不推荐与已发内容重复的选题（自备合集进度或已发清单即可）。
- 选写作参考账号时按账号质量挑，不按点赞量排序；每个号至少读近 3 个月代表作 10 篇，质量一般的号不凑数。

## 2. 七项门槛（逐项过，任一不过不发）

1. **有增量**：至少带下面 §3 的一种增量。只有官宣标题和功能复述的，不发。
2. **有出处**：重要事实能回到原始链接与日期；媒体转述追到一手；来源缺失就删掉该事实，不用模糊的专家背书。
3. **解释得通**：说清输入是什么、谁处理、怎么得到输出。只观察到现象就只写现象，不补一个听起来合理的原理。
4. **亲测可查**：留输入、产品版本、环境、结果和失败记录（流程见 §4）。性能数字带硬件、并发、对照配置；来源作者做的测试不写成自己测的。
5. **判断有用**：至少帮读者做一项选择：怎么验证、谁批准、怎样维护、代价由谁承担。没有依据的预测不写成事实。
6. **承诺不过量**：标题、封面、正文指向同一件事，标题不吹。演示只能说明演示场景，测试通过只能说明被测部分，来源验真只能证明出处、证明不了答案正确。
7. **图有依据**：每个数字、箭头、表格单元都能回查材料；先有信息再选图。

## 3. 九种增量（每条至少一种）

补机制（为什么）· 换一个框（放进旧谱系或行业趋势）· 亲手的数据点或真实做法 · 把问题往前推一步（真正难的是证明、维护还是付费）· 用激励逻辑推演（谁得到什么，所以会怎样）· 带约束的追问 · 带适用条件的立场 · 和主流相反的预测 · 精确区分或命名一个现象。夸也要具体：说清程度和原因。

## 4. 先实测再写

稿里出现的命令、CLI、配置改动、自查步骤、复现过程、工具对比，发布前都在隔离环境里真跑一遍：

1. 环境：临时目录 + 假 `HOME`（`export HOME=$(mktemp -d)`）、venv、或 Docker；装来源里写的真实版本。
2. 运行并留日志到 `<稿目录>/verify/`（命令、版本号、输出、退出码）。
3. 对比类：给前后差异（`diff`、截图）或多次运行数据，不只跑一次。
4. 写进稿件时用肯定、具体的陈述：「沙箱里装 0.7.1 后实测：remove 清掉了 X，Y 要手动删」。
5. 跑不了的那条：删掉，或只陈述来源原话（「官方 README 写明……」「issue 里的日志显示……」）。不写「没测」来兜底。
6. 诚实交代：自己造的测试环境、自己埋的 bug、自己写的基线，在句中如实写明，用陈述口吻，不用道歉口吻。

## 5. 素材清单（内部底稿，不进成稿格式）

作者与日期、原始链接、产品全称、谁做了什么、数字出处、自己实测了什么、尚未核实的说法、每张图的依据。存为 `<稿目录>/sources.md`。

## 自查

```bash
test -s <稿目录>/sources.md && rg -c "https?://" <稿目录>/sources.md   # 有来源链接
ls <稿目录>/verify/                                                     # 稿里有命令/对比时必须非空
rg -n "未实测|未复现|没实测|没跑过|未验证|本机未" <稿目录>               # 应为 0 行
```
